# Steam and games

Measured facts about Steam and games, for M8 (games and Steam) and M9 (every ARM64) of `roadmap.md`; what is missing and in what order is in `analysis.md`. Every statement is marked ✅ (verified, with how) or ⚠️ (to verify, with how). Host: Raspberry Pi 5 with the 4K kernel since 2026-10-14 (`environment.md`), except where stated otherwise. The measurements of the engines (box64, FEX, Valve's FEX layer) are in `tech/engines.md`.

Layers (ADR-0032, ADR-0034): the Steam client is Valve's native ARM64 one; Windows games go through Proton ARM64 (with FEX); x86 Linux games run under armor; graphics are the host's Mesa. The i386 client under armor remains only as a fallback for 16K systems.

## Valve's native ARM64 client
Details and method in `tech/engines.md`; in summary:
- ✅ manifest `steam_client_linuxarm64`, platform `linuxarm64`, version `1791918634`, the same as the x86 client (downloaded on 2026-10-14);
- ✅ the native binaries are in the package `bins_linuxarm64_linuxarm64`, directory `steamrtarm64/`: 43 aarch64 ELFs (`steam` of about 10 MB, `steamwebhelper`, `steamui.so`, `steamclient.so`, …), counted with `file`; the bootstrap package `steam_linuxarm64` still contains the i386 bootstrapper, and `bins_linuxarm64` x86 binaries;
- ✅ the client's ELF segments are 4K-aligned (`0x1000`) and code and data share a 16K page (`readelf -lW`): on the Pi 5's 16K kernel it terminates immediately with SIGSEGV;
- ✅ with the 4K kernel (2026-10-14) it updates itself (667 MB in less than a minute), asks for three host libraries (GTK2, IBus, PipeWire, found with `ldd` and installed by hand), and on the real desktop the user signs in and the library opens (a trial installation, removed on 2026-10-15; since then `armor install steam`, below);
- ✅ on its own it installs Valve's FEX layer (`FEX-Emu`, FEX-2607, interface `emulator_v0`), the Steam Linux Runtime 4.0 and Proton Experimental, both x86-64 and ARM64 (`tech/engines.md`, "Valve's FEX layer"). ⚠️ No Windows game run with Proton yet: to verify with a simple Windows game from the library (M8);
- ⚠️ Valve declares Steam for Linux on ARM unsupported outside its own hardware: to verify again on Valve's support page.

### Installed by armor (since 2026-10-15, ADR-0038)
- ✅ **`armor install steam`** in a separate data directory (`XDG_DATA_HOME=target/steamtest`): Valve's manifest read over HTTPS, the three packages `steam_linuxarm64` (4 MB), `bins_linuxarm64` (76 MB) and `bins_linuxarm64_linuxarm64` (110 MB) downloaded and checked against the manifest's size and SHA-256, unpacked, in 28 s; the menu entry "Steam" written. Two facts found on the way: Valve's zips carry no permissions (the client did not start: `Permission denied`), so armor makes the ELF files and scripts executable; the client refuses to start without `~/.steam/steam` ("Steam data link does not exist, client is misconfigured"), so armor makes the links `steam`, `root` and `bin64` that `steam.sh` would make.
- ✅ **First start with `armor run Steam`:** the client downloads its update (the directory grows from 533 MB to 3.1 GB in about a minute), exits with 42 ("Update complete, launching…"), armor starts it again, and the "Sign in to Steam" window appears on the desktop (screenshot, 2026-10-15), while the hand-installed client of 2026-10-14 was running with its own `HOME`.
- ✅ **Games need `~/.steam/sdkarm64`** (2026-10-15): the ARM64 client starts every game as `~/.steam/sdkarm64/steam-launch-wrapper -- …/reaper SteamLaunch AppId=… -- <compatibility tools> <game>`; Valve's `steam.sh` (written for x86) makes `sdk32` and `sdk64` but not `sdkarm64`, so a game ended within a second ("Game process removed"). armor links `sdkarm64` to `linuxarm64/` (which holds `steam-launch-wrapper` and `steamclient.so`), and `sdk32`, `sdk64`, `bin32` as `steam.sh` does.
- ✅ **Which Proton:** with Steam Play on, the client chose "Proton Experimental" for Doki Doki Literature Club and downloaded its Windows build; that Proton is x86-64 (`files/bin/wine` an x86-64 ELF), run through Valve's FEX layer and the Steam Linux Runtime 4.0 (`fex-compat-tool` → `_v2-entry-point` → `proton`, `compat_log.txt`). "Proton Experimental (ARM64)" (ARM64X Wine, `tech/engines.md`) is a separate tool, chosen in the game's compatibility properties.
- ✅ **The first Windows game with ARM64 Proton** (2026-10-15): Doki Doki Literature Club's Windows build (`DDLC.exe`, Ren'Py) with "Proton Experimental (ARM64)" (Steam appid 4427310, 2.0 GB), started by the client through `linuxarm64/steam-launch-wrapper`, `reaper`, `pw-audio-namespace` and the ARM64 Steam Linux Runtime 4 container (`SteamLinuxRuntime_4-arm64`, `pressure-vessel`, `srt-bwrap`). It opens its menu and its first dialog (screenshot). Its own log (`log.txt`): Windows 8 as Wine reports it, OpenGL "Vendor: 'Broadcom', Renderer: 'V3D 7.1.7.0', Version: '3.1 Mesa 26.2.2'", that is the Pi's GPU through the host's Mesa. `pactl list sink-inputs`: a running stream from `DDLC.exe` (`wine-preloader`) into PipeWire. Two things on the way: the first launch waited forever on "Downloading Content (0%)" after the shader cache check (`CheckShaderDepotManifest`, a download queue left suspended by a restart of the client); with "Shader Pre-Caching" off in Steam's settings it started. ⚠️ Steam's in-game overlay (FPS counter, Shift+Tab) does not appear: the client starts the ARM64 `gameoverlayui` for the game process ("GameOverlay: started …" in `console_log.txt`), but the part drawn inside the game is x86 DLLs (`GameOverlayRenderer.dll`, `GameOverlayRenderer64.dll`), and with ARM64 Proton the game's OpenGL goes to the host's native Mesa; to verify on a newer Proton (ARM64) and client; an alternative counter is MangoHud (ARM64). Steam had first chosen the x86-64 "Proton Experimental" (run entirely under FEX); the ARM64 one is chosen in the game's compatibility properties.
- ✅ The package `bins_linuxarm64` had changed since 2026-10-14 (new file name and SHA-256 in the manifest): the reason not to pin the client's packages (ADR-0038).

## The first x86 game under armor: Doki Doki Literature Club (2026-10-14)
Free, appid 698780, Ren'Py engine; the x86-64 Linux build (with Python 2.7) installed by the ARM64 client into its library. Level 1 in `COMPATIBILITY_MATRIX.md`.
- ✅ **Under `qemu-x86_64`** (the reference) it opens; Ren'Py warns that rendering is in software.
- ✅ **Under armor** (`armor --root target/guest/rootfs-games ./DDLC.sh`, from the game's directory, on the real desktop) it reaches the game's first scene with complete graphics. Observed during the test, not measured with `bench`: about 40% CPU and 750 MB of memory.
- ✅ **What was missing on 2026-10-14** (messages from the game and from Mesa under armor): audio (ALSA: "Unknown PCM default": no sound server ran, below); the GPU: the root's x86 Mesa has no driver for the Pi's GPU (`vc4: driver missing`), so it drew in software (llvmpipe), as under qemu. Both solved on 2026-10-15 (below).
- ✅ **GPU, measured on 2026-10-15:** Debian's amd64 Mesa (25.0.7, in the games root) has no driver for the Pi's GPU: its `dri/` holds crocus, d3d12, i915, iris, kms_swrast, nouveau, r300, r600, radeonsi, swrast, virtio_gpu, vmwgfx and zink, `libgallium` prints `v3d: driver missing` and `vc4: driver missing`, and its Vulkan drivers are Intel, AMD, Nouveau, virtio, gfxstream and lavapipe, no Broadcom one; the host's arm64 Mesa has `v3d_dri.so` and `vc4_dri.so`. So the GPU needs one of two routes: an x86-64 Mesa built with the v3d driver (and armor passing the v3d DRM ioctls through), or calls from x86 code to the host's own libraries (the roadmap's route). Chosen on 2026-10-15: calls to the host's own libraries (ADR-0041).
- ✅ **On the Pi's GPU, 2026-10-15** (ADR-0041): `armor --host-gl --root target/guest/rootfs-games ./DDLC.sh`. The game's log: "Vendor: 'Broadcom' Renderer: 'V3D 7.1.7.0' Version: '3.1 Mesa 26.2.2'", "Using shader environment", "Using gl renderer", textures up to 2048 px work, 5 test frames in 0.23 s. Its music plays (recorded from the sink's monitor, peak 11268), and it is playable: a new game, the player's name typed into its dialog, the first scene and its lines advanced with the mouse (screenshots). Observed, not measured with `bench`: about 590 MB, and about 150% CPU on the first scene, of which one guest thread takes a whole core in SSE floating-point arithmetic that the JIT leaves to the interpreter (`perf record -t`: `armor_cpu::float::arith`, `f80::round`, `f80::add_signed`), a target for `tech/performance.md`. Before, Ren'Py had silently used its own software renderer, because `libXmu` (which its GL module links) was missing from the root: added to the games root with `libGLU`, `libXt`, `libSM`, `libICE`, `libOpenGL` and `libuuid`.
- ✅ **Audio, measured on 2026-10-15:** on the development Pi no sound server ran at first (PipeWire, `pipewire-pulse` and WirePlumber installed, but never started); since 2026-10-15 they run as user services (`pactl info`: "PulseAudio (on PipeWire 1.4.2)"). No HDMI display is connected, so both `vc4-hdmi` cards are off and the default output is PipeWire's null sink. The games root has ALSA's configuration (`alsa.conf`) and `libpulse0`, but not ALSA's plugins (`alsa-lib/`), hence "Unknown PCM default". ✅ With PipeWire running (2026-10-15), the game's Linux build under armor (the games root, from the files Steam installed) plays its music through the x86 PulseAudio client in the root and the host's socket in `$XDG_RUNTIME_DIR/pulse/native`, with no change to armor: `pactl list sink-inputs` shows a running stream from `DDLC`, and four seconds recorded from the null sink's monitor (`parecord`) hold sound (peak 11268 of 32767, 99% of the samples not zero). So sound for x86 Linux games does not need calls to the host's libraries; graphics do.
- ✅ **How what was needed was found** (each addition with its test, identical to qemu and to the Xeon where it runs): the 80 distinct syscalls the game makes under `qemu-x86_64 -strace`, compared with armor's table, then the requests found by running it. armor gained: `fork` from a guest with several threads; record locks (`F_GETLK`/`F_SETLK`/`F_SETLKW` and OFD, also with the i386 structures); `memfd_create` and seals; priority-inheritance futexes; System V shared memory for x86_64 (X11's MIT-SHM); `clock_getres`, the `sched_*` calls, `getresuid`/`getresgid`, `sched_setaffinity`, `fallocate`; the ioctls `DRM_IOCTL_VERSION`, the dma-buf ones without pointers, and EBADF for an unknown request on a closed descriptor. Details in `tech/syscalls.md`, tests in `testing.md`.
- ✅ **The root `target/guest/rootfs-games`** (outside the repository; since 2026-10-15 built by `cargo xtask fetch-rootfs --games`, 84 packages pinned by SHA-256 in `xtask/src/rootfs.rs`, the same files as the root prepared by hand on 2026-10-14 plus the 7 packages above: `diff -r` between the two shows only Python's `__pycache__`): the amd64 test root plus Debian trixie amd64 packages (the closure of `libgl1`, `libgl1-mesa-dri`, `libglx-mesa0`, `libegl1`, `libegl-mesa0`, `libgles2`, `libx11-6`, `libxext6`, `libxrandr2`, `libxi6`, `libxcursor1`, `libxinerama1`, `libxxf86vm1`, `libxrender1`, `libxfixes3`, `libxss1`, `libxkbcommon0`, `libasound2t64`, `libpulse0`, `libudev1`, `libdbus-1-3`, `libvulkan1`, `mesa-vulkan-drivers`, `libsdl2-2.0-0`, then `libstdc++6`, `libxmu6`, `libglu1-mesa`, `libopengl0`, minus those already in the test root), each with its SHA-256 from the `Packages` index (itself verified against `Release`), only extracted.

## The i386 client under armor: fallback for 16K systems
Steam's classic Linux client is an i386 PIE (`ubuntu12_32/steam`, from the bootstrap of `steam.deb`: 54 ELFs, 39 of them 32-bit ✅ `armor inspect` and `readelf`, 2026-10-13) with 2,567 MMX instructions ✅ (`armor inspect`, 2026-10-14), which armor runs since 2026-10-14 (ADR-0029). ✅ Under armor, on the 16K kernel, the client launched directly (i386 root, with the HOME and the links that `steam.sh` prepares, in `target/steam-probe/`) downloads, extracts and installs the 503 MB of the update without a display in 4.5 minutes and exits with 42 as under `qemu-i386`; the 13,277 installed files are byte-for-byte identical to those of the installation done under qemu. Getting there required 29 i386 syscalls and the JIT translation of MMX, `pshufb` and `palignr` (`tech/jit.md`, "MMX and SSSE3"). ⚠️ Not tried: the whole `steam.sh`, the interface (`steamwebhelper`, Chromium) and the Steam Runtime under armor. If it is needed, it will be one of the M9 routes for systems where the ARM64 client does not start.
