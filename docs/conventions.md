# Conventions

## Language
- **All documentation** (including `README.md`, the entry point for the community): English.
- **Identifiers, code comments, commit messages:** English.
- **Error messages for the user:** English, to be revisited if localisation is added.

## Rust
- Toolchain: **stable via rustup**, pinned to the `stable` channel with `clippy` and `rustfmt` in `rust-toolchain.toml`. Version at installation time: 1.99.0.
- Edition **2024**, set once in `[workspace.package]` of the root `Cargo.toml` and inherited by the crates.
- Every crate inherits `version`, `edition`, `license`, `repository` and `publish` from the workspace, and the lints with `[lints] workspace = true`.
- `publish = false` until the name is checked on crates.io.
- Before considering a piece of work finished:
  ```bash
  cargo fmt --all --check
  cargo clippy --workspace --all-targets -- -D warnings
  cargo test --workspace
  cargo xtask difftest
  cargo xtask decoder-check target/guest/c/* target/guest/busybox/busybox target/guest/rootfs/usr/bin/ls target/guest/rootfs/usr/lib/x86_64-linux-gnu/libm.so.6 target/guest/rootfs/usr/lib/x86_64-linux-gnu/libcrypto.so.3
  cargo xtask encoder-check
  cargo xtask progress --check
  cargo xtask coverage --check
  ```
- **External dependencies** (ADR-0008): only `libc`, and only in the crates where `unsafe` is allowed. Any other dependency requires a new ADR with a license check.

## `unsafe` policy
- The pure crates (`armor-elf`, `armor-x86`, `armor-cpu`) and the `armor` binary declare `#![forbid(unsafe_code)]`.
- `unsafe` is allowed only in the crates listed in `architecture.md` (`armor-mem`, `armor-linux`, `armor-jit` and the bare minimum elsewhere).
- Every `unsafe` block has a `// SAFETY:` comment that explains why the invariants hold. This is enforced by the lint `clippy::undocumented_unsafe_blocks = "deny"` in the workspace; in addition `unsafe_op_in_unsafe_fn = "deny"`.
- Guest addresses and host pointers do not mix: guest addresses are `u64` in all APIs, while host pointers exist only inside `armor-mem`, in the `libc` calls of `armor-linux` on armor's buffers and in `armor-jit` (code buffer, translated blocks). The only public API of `armor-mem` that returns a host pointer is `MemView::page_table`, the permission table read by the generated code (ADR-0021).

## Error handling
- A guest input (malformed ELF, unknown opcode, unsupported syscall) must **never** cause a `panic!`. It produces a structured error with RIP and the instruction bytes.
- An unimplemented instruction or syscall produces an explicit error and a dedicated exit code, never a silently wrong result.
- **How armor terminates:**

  | Situation | Effect |
  |---|---|
  | the guest calls `exit`/`exit_group` | same exit status as the guest |
  | guest memory fault, #GP (`hlt`, misaligned SSE, instruction longer than 15 bytes) | message `armor: guest …` on stderr, then armor terminates with **SIGSEGV** |
  | #UD (instruction invalid in 64-bit mode, `ud2`, LOCK not allowed) | message, then **SIGILL** |
  | #DE (division by zero or quotient too large) | message, then **SIGFPE** |
  | #BP (`int3`) | message, then **SIGTRAP** |
  | armor error: wrong usage, program not loadable, instruction or syscall not yet supported | message `armor: …`, exit code **125** |
  | armor bug: a `panic!` in any thread (including a difference found by lockstep, `tech/jit.md`) | panic message, exit code **125** (since 2026-10-12; before, a panic in a guest thread stopped only that thread) |

  125 can coincide with an exit status chosen by the guest: the message on stderr tells them apart.
- Logging: there is no logging system. Diagnostics on stderr with the prefix `armor:`; two debug environment variables: `ARMOR_JIT_STATS` (JIT statistics at exit; with the value `interpreted` also the instructions left to the interpreter, by type: `tech/performance.md`) and `ARMOR_GIL=1` (serialised threads, ADR-0023); `ARMOR_HOST_FEATURES=baseline` (the JIT uses only ARMv8.0, ADR-0032). Levels and flags to be decided when needed.

## Documentation
- General rules: docs updated with every change, an ADR for every decision, the verification chain (`testing.md`) green before every commit.
- In the `docs/tech/` files every statement is marked:
  - ✅ **verified**, with an indication of how (command, header, manual section);
  - ⚠️ **to verify**, with an indication of how to verify it.
- Dates in the documents are **absolute** (YYYY-MM-DD).
- **Completion percentages in the README:**
  - they are generated by `cargo xtask progress` (`xtask/src/progress.rs`) by counting the top-level checkboxes (`- [x]` / `- [ ]`) of every `## M<n>` section of `roadmap.md`; indented sub-items do not count;
  - the block between `<!-- progress:start -->` and `<!-- progress:end -->` is not edited by hand;
  - `cargo xtask progress --check` fails if the README is not up to date;
  - the English milestone names are in `MILESTONE_NAMES` (`xtask/src/progress.rs`): a new milestone must be added there, otherwise the command gives an error;
  - the badges are static shields.io images: the URL contains only the label and the percentage.
- **Coverage badges in the README** (since 2026-10-12): generated by `cargo xtask coverage` (`xtask/src/coverage.rs`) between `<!-- coverage:start -->` and `<!-- coverage:end -->`.
  - **x86 decoder:** share of the instructions of `c/hello` (static glibc) decoded with the same length as objdump, with one decimal place; uses `decoder-check`.
  - **syscalls:** numbers for which `armor_linux::syscall::is_implemented` is true, out of those defined in `/usr/x86_64-linux-gnu/include/asm/unistd_64.h`. `is_implemented` is kept aligned with `dispatch` by the test `implemented_list_matches_dispatch`.
  - It needs the x86_64 toolchain, unlike `progress`; `--check` fails if the README is not up to date.
- The code does not duplicate the documentation: comments explain the local *why*, the docs the overall picture.

## Licenses and third-party code
- Do not copy code from qemu (GPL-2.0).
- MIT code (box64, FEX) may be consulted. If a part of it is reused, it must be attributed in the file and in the README.
- Details in `references.md`.
