# Architecture

**State (2026-10-14):** M0–M6 (the engine) completed; M7–M10 open (`roadmap.md`, ADR-0034). armor runs static x86_64 and i386 executables (`ET_EXEC` and static-pie) and dynamic ones (PIE with the real `ld.so` from the guest root), with threads in parallel, signals and processes, interpreted or translated to AArch64 by the JIT (the default); for Windows programs it prepares Hangover and one prefix per application (`armor install`); for x86-64 Debian packages, AppImages and `.tar.*` archives, one root per application with the verified Debian packages they need (since 2026-10-14, `debs.rs`). The sections marked *(planned)* describe the design not yet implemented: they must be updated when the code implements them or contradicts them.

## Application layers (ADR-0032, ADR-0034)
armor is one of the components of a broader application, not the only engine. Its three roles: **engine** for x86 Linux programs, **glue** around the external components (Windows, Steam), **test bench** for all engines.
| Layer | Component | State |
|---|---|---|
| x86 Linux programs (x86-64, i386) | armor (this document); then direct calls to the host's native libraries | armor ✅; native libraries *(planned)*, M8 |
| Windows programs | Hangover (ARM64X Wine with FEX), DXVK; armor downloads them (`armor engine fetch`) and prepares one prefix per application (`armor install`) | ✅ 7-Zip; automatic steps (Wine Mono, GPU, runtime) *(planned)*, M7 |
| Steam client and Windows games on Steam | Valve's native ARM64 client, ARM64 Proton with FEX | the client signs in ✅ (4K pages, `tech/engines.md`); installed by armor, and Proton *(planned)*, M8 |
| graphics | the host's Mesa drivers | *(planned)* |
| systems where the external components do not start (16K pages) | armor, or a way still to be chosen | *(planned)*, M9 |
| startup | armor's CLI recognises the file and chooses the path (ADR-0028, below) | path for x86-64/i386 ELF, AArch64 and scripts ✅; double click and interface *(planned)*, M7 |
| test bench | `cargo xtask difftest` with armor, box64 or FEX on the same cases (`--engine`, `testing.md`) | ✅ since 2026-10-14; matrix generated from the measurements *(planned)*, M10 |

## Execution flow (implemented)
1. **CLI** (`crates/armor/src/main.rs`): `armor [--jit | --interpreter | --lockstep] [--root DIR] [--argv0 NAME] [--host-gl] <program> [args…]`, or `armor inspect <file>` (below, `inspect.rs`), or the commands for installed applications `armor install [--name NAME] [--pause] <file.exe|file.msi|file.zip|file.deb|file.AppImage|file.tar.*> [-- arguments]`, `armor run <app> [arguments]`, `armor list`, `armor remove <app>`, `armor engine fetch` (`engines.rs`: downloads Hangover, DXVK and Wine Mono, pinned by size and SHA-256, and extracts them without installing them) (`apps.rs`, ADR-0033: one Wine prefix per application in `$XDG_DATA_HOME/armor/apps/<name>/`, ARM64X Wine with FEX from `ARMOR_WINE` or `$XDG_DATA_HOME/armor/engines/wine/usr/bin/wine`; the shortcuts that Wine creates end up in the application's `menu/` folder and armor writes the `armor-<name>-<n>.desktop` entries in `$XDG_DATA_HOME/applications`, with `Exec` = `armor run`). The prefix's `Desktop` becomes a folder of its own (Wine links it to `~/Desktop`, where installers would leave shortcuts with a `wine` that is not in `PATH`); if `$XDG_DATA_HOME/armor/engines/dxvk` contains DXVK, its x86-64 DLLs (`x64/`) go into `system32` and the 32-bit ones (`x32/`) into `syswow64`, with Wine's overrides (the ARM64EC build stopped the Epic Games Launcher, `tech/engines.md`). Wine Mono (.NET) goes into every new prefix, as Wine itself does, and `mscoree` is then enabled. The kernel driver of the host's GPU render nodes (`/sys/class/drm/renderD*`) picks DXVK's renderer: where every GPU uses a driver DXVK refuses (a measured table, today `v3d`), `DXVK_FILTER_DEVICE_NAME=llvmpipe`, written with its reason. Without `--name`, the application is named after the Start Menu folder that directly holds most of its shortcuts, uninstallers left out (`7-Zip`; `hicloud/Ezviz Studio/…` → `Ezviz-Studio`), else after its first shortcut. Shortcuts to uninstallers (`Uninstall …`) get no menu entry: `armor remove` removes the application. After the installer ends, armor waits at most 60 s for the processes it left in the prefix (msiexec, Wine's menu builder); programs still running then (an updater, or the program started at the end of the installation) are named and left running, and the menu entries are written anyway (until 2026-10-14 armor waited for them forever: EZVIZ Studio's updater kept the installation from ending). An installer that fails without creating a menu entry leaves nothing behind. `armor list --porcelain` prints a stable tab-separated format for programs (the window). The window is a separate program, `armor-gui` (`gui/`, its own Cargo workspace with GTK 4, ADR-0035), which runs these commands. Since 2026-10-14 (redone, still GTK 4 only, styled with its own CSS on the theme's colours): a grid of cards (`FlowBox`, one to eight per line as the window's width allows) with each application's icon (the fourth field of `armor list --porcelain`'s `entry` lines), name, a Windows or Linux badge, Open (the first menu entry; a double click on the card does the same) and a menu with the other entries and Remove (the confirmation worded by kind); a search field in the header (typing anywhere searches); a page for no applications and one for no match; the engine notice as a banner; tasks (`install`, `remove`, `engine fetch`) in a panel at the bottom with a progress bar and a status line read from armor's messages (`progress_of`: `N of M packages unpacked`, `downloading …`, curl's percentage, `… installed`), the full output under Details; short notices ("Opening …") at the bottom; installers dropped on the window are installed. Nothing that can wait runs on the window's thread: `armor list` runs with `gio::spawn_blocking`, commands on threads, and every `armor run` it starts is reaped by a thread (`armor run` itself reports a failed start in a desktop notification). A `gio::FileMonitor` on `$XDG_DATA_HOME/armor/apps` refreshes the window when an application is installed or removed outside it. Since 2026-10-15 its menu (☰) has **Install Steam** and **Check for updates**, and once a day it checks for a newer armor and shows a notice with **Update**, then **Restart**. **`armor update`** (`update.rs`, ADR-0039): the newest release with an arm64 package (pre-releases included) from GitHub's API, read with a small JSON parser of its own (the engine depends only on `libc`), compared with the installed package (`dpkg --compare-versions`), downloaded, checked against GitHub's SHA-256 digest of the asset, installed with `pkexec apt-get install`; `--check [--porcelain]` only checks. `--pause` waits for Enter at the end: the desktop entry "Install with armor" of the package (`cargo xtask package`) runs `armor install --pause %f` in a terminal window for a double-clicked `.exe`, `.msi`, `.deb` or AppImage. The kind of file is recognised from its contents (`installer_kind`): PE, MSI (OLE compound file), zip (`PK\x03\x04`), `ar` archive with `debian-binary`, ELF with `AI\x02` at `e_ident[8..11]` (AppImage of type 2), gzip/xz/bzip2/zstd or `ustar` (tar archive). **x86-64 `.deb`** (since 2026-10-14, `crates/armor/src/debs.rs`, ADR-0033): the control file is read from the package (an `ar` reader in Rust, then the host's `tar`); `arm64` packages are refused with a suggestion to use apt, other architectures refused. `Pre-Depends` and `Depends` are resolved, recursively, against the amd64 archive of the host's distribution (`/etc/os-release`: Debian bookworm, trixie, forky from deb.debian.org `main`; Ubuntu from archive.ubuntu.com `main` and `universe`): for each dependency the first alternative that exists as a package or as a provider, version constraints and `:any` dropped, the packages a plain unpack does not need skipped (`NOT_NEEDED`: debconf, dpkg, install-info, init-system-helpers, adduser, passwd, systemd, base-passwd…). The archive's `InRelease` is verified with `gpgv` and the archive keyring, `Packages.xz` against its SHA-256 in the verified release; the index is cached for a day. Every package is downloaded into a cache shared by all applications (`$XDG_DATA_HOME/armor/cache/debs/`), checked against the index's SHA-256 and only unpacked — no maintainer scripts, no root — into `$XDG_DATA_HOME/armor/apps/<name>/root`; `dash`, `bash` and `coreutils` are always added, for the scripts that start many programs. Then the shared libraries the package's own ELF files need (`DT_NEEDED`) and that neither the package nor the root has are looked up in the archive's `Contents-amd64` index (verified like `Packages`) and their packages added, with their dependencies (XnView MP bundles Qt but needs 59 more system packages this way). Menu entries come from the main package's visible `.desktop` files anywhere under `usr/share` (Spotify keeps its own in `/usr/share/spotify/`): `Exec` resolved in the root (`env VAR=…` dropped; field codes like `%U` kept for the desktop), icons from the root (hicolor, pixmaps, else the largest PNG in an `icons/` directory next to the `.desktop` file); the application is named after the first entry. `armor run <app>` then runs `armor --root <root> --argv0 <guest path> <program resolved in the root>`; symbolic links with absolute targets are followed inside the root (`resolve_in_root`). If anything fails, nothing is kept. **AppImages** (type 2, since 2026-10-14): first the system base most AppImages expect and do not carry (`APPIMAGE_BASE`: glibc, X11, xcb, Wayland, fontconfig, freetype, GL, GTK 3, `dash`, `bash`, `coreutils` …, with their dependencies) from the same verified archive into the root; then the AppImage's own runtime runs under armor (`armor --root <root> <file> --appimage-extract`, in the application's directory) and its `squashfs-root` becomes `/opt/appimage` in the root; the libraries its files still miss are added as for a `.deb`. Menu entries from the AppDir's `.desktop` file, with `Exec` = `/opt/appimage/AppRun` and the entry's arguments; `APPDIR` and `APPIMAGE` in `app.conf`. **`.tar.*` archives** (since 2026-10-14): the same system base, then the host's `tar` unpacks the archive; a single top directory goes to `/opt/<that directory>` (where such archives expect to be: the `.desktop` file of Sublime Text runs `/opt/sublime_text/sublime_text`), otherwise everything goes to `/opt/<name>`; missing libraries added as above. Menu entries from the archive's `.desktop` files (a program not found at its absolute path is looked up by name among the archive's files, an icon by name among its PNGs), else one for each graphical program (an executable ELF with an interpreter that needs X11, xcb, Wayland, GTK, Qt, SDL, GL or Vulkan, at most three directories deep); command-line programs get no entry and `armor install` says where they are. For every Linux application, `app.conf` sets `QT_XCB_GL_INTEGRATION=none`, with the reason (an open armor issue, `tech/syscalls.md`, `futex`). **Windows zips** (since 2026-10-15, `install_zip`): the entries are listed with `unzip -Z1`; with a single top directory, it is the zip's root. The programs are the `.exe` files at the shallowest depth that has any, helpers left out (`is_helper_program`: installers, uninstallers, crash reporters, redistributables, updaters). A portable program (most games of itch.io) is unpacked into `C:\Games\<name>` of a new prefix (Steam's ARM64 Proton when Steam is installed, its prefix made with `wineboot`; else Hangover), named after its single program or its top directory, with a menu entry per graphical program (PE subsystem 2, `inspect::pe_subsystem`; every program when none is graphical), its icon from the program's PE resources; a zip with only an installer (`setup`/`install` in its name, or a lone `.msi`) is unpacked into the cache and the installer run as for an `.exe`. `armor run` starts a Windows program given by its path (`C:\…\x.exe`) in that program's folder (`program_command`), as Explorer does, without Wine's `start` (a console program: a console window opened next to the game). The prefix also gets `MESA_GL_VERSION_OVERRIDE=3.3` and `MESA_GLSL_VERSION_OVERRIDE=330` when every GPU is a `v3d` (`gl_settings`: the Pi's OpenGL driver reports 3.1, and programs that ask for GLSL 1.50 refused to start; written into `app.conf` with the reason). **Windows programs with Steam's ARM64 Proton** (since 2026-10-15, ADR-0040): when the Steam client installed by armor has "Proton Experimental (ARM64)" and the ARM64 Steam Linux Runtime 4 (`SteamLinuxRuntime_4-arm64`), `armor install` of an `.exe` or `.msi` uses them instead of Hangover (`install_with_proton`): the prefix is `<app>/proton/pfx` (`STEAM_COMPAT_DATA_PATH=<app>/proton`, `STEAM_COMPAT_CLIENT_INSTALL_PATH` the client), and the installer, and later the program, run as `_v2-entry-point --verb=waitforexitandrun -- <Proton>/proton waitforexitandrun <program>` (`proton_command`; Steam need not be running); `app.conf` records `engine = proton`, and `engine_command` picks the engine for `armor run` and for the Visual C++ runtime. Proton does not run Wine's menu builder, so the menu entries come from the prefix's Start Menu shortcuts, read by armor (`shortcuts.rs`: the `.lnk` format, MS-SHLLINK, for target, arguments and icon location; the icon group of the program's PE resources written out as an `.ico` in `<app>/icons/`); the entry opens the shortcut with Wine's `start.exe /wait`, which applies its working folder. Without Steam's Proton, Hangover as before. **Steam** (since 2026-10-15, `crates/armor/src/steam.rs`, ADR-0038): `armor install steam` installs Valve's ARM64 client as an application of kind `steam`: it checks 4K pages and the three host libraries the client loads (GTK 2, IBus, PipeWire; else the `apt` line), reads Valve's manifest `steam_client_linuxarm64` over HTTPS, downloads the packages `steam_linuxarm64`, `bins_linuxarm64` and `bins_linuxarm64_linuxarm64` (cached in `$XDG_DATA_HOME/armor/cache/steam/`), checks each against the manifest's size and SHA-256, unpacks them with `unzip` into `<app>/Steam`, makes the ELF files and scripts executable, and writes the `~/.steam` links (`steam`, `root`, `bin64`, `bin32`, `sdk32`, `sdk64`, `sdkarm64`) into its own `HOME`, `<app>/home`. `armor run Steam` starts `steamrtarm64/steam` there with that `HOME` (the real home's `.Xauthority` for X), again whenever it exits with 42 (after updating itself; at most five times). The application's `app.conf`: `kind` (`windows`, `linux` or `steam`), `dxvk = yes|no`, `mono = yes|no`, `vcredist = yes` (once armor installed the Visual C++ runtime), `engine = proton`, `host-gl = yes|no` (a Linux program's OpenGL through the host's libGL, ADR-0041; `armor run` then adds `--host-gl`), `env = NAME=VALUE`, with a comment for each variable armor chose. **`armor run`** (since 2026-10-14) does not replace itself with the program: it waits for it, passes its standard error through and keeps it in the application's `last-run.log` (at most 4 MiB), and reads it for failures (`failure_in_line`): Wine's loader errors for a missing DLL (Wine runs with `WINEDEBUG=-all,err+module`; they count only with Wine's `Importing dlls for L"<program>" failed` line, since a running program that probes an optional DLL prints the first kind too), Wine's `Unhandled …` crash line, armor's own stop messages; a signal that ends the program (not `SIGINT`, `SIGTERM`, `SIGHUP`) counts too. It then says what happened in one line (`explain_run`) on standard error and, when standard error is not a terminal (started from the menu or the window), in a desktop notification (`gdbus` to `org.freedesktop.Notifications`). After exit status 0 nothing is reported; a plain non-zero exit is only printed: programs use them on purpose. When a Windows program cannot start because a library of the Microsoft Visual C++ 2015–2022 runtime is missing (MFC: Wine has the rest), `armor run` fetches Microsoft's redistributables (x64 and x86, version 14.44.35211, versioned URLs pinned by size and SHA-256 in `engines.rs`, cached in `engines/vcredist-<version>/`), installs them silently in the prefix, writes `vcredist = yes` with the reason, and opens the program again. The exit status of `armor run` is the program's. It chooses the path from the file (ADR-0028, `choose_path`): x86-64 → armor with the JIT by default (`--interpreter` for the interpreter alone); AArch64 → run directly with a warning; `#!` script → the interpreter, under armor if x86-64 (resolved in the guest root), otherwise on the host; a script of the host system (in `/usr`, `/bin`, `/sbin`, `/lib`, `/lib64` or `/etc` and not overridden by the root, such as Debian's `/usr/bin/chromium` launcher) always on the host, with the host's interpreter, also from a guest's `execve` (since 2026-10-15); the rest → refused with a reason and a suggestion (`inspect::suggestion`). `--diagnose[=FILE]` (`diagnose.rs`): at the end a report on path, exit, ENOSYS, faults, stop and JIT, with suggestions and without guest data; `execve` passes it to the children. When armor stops it still prints a "suggestion:" line if it has one (`diagnose::stop_suggestion`). **Profiles** (`profile.rs`, ADR-0028): `$XDG_CONFIG_HOME/armor/profiles/<name>.conf`, otherwise `~/.config/armor/profiles/`; chosen with `--profile NAME` (it must exist) or, if there is one, the one with the name of the program's file. Lines `key = value`, `#` comments; keys `engine` (`jit`, `interpreter`, `lockstep`), `root` (empty: no root), `argv0`, `diagnose` (`stderr` or a file), `env = NAME=VALUE` and `unset = NAME` (repeatable, on the guest's environment), `sandbox = yes|no`, `allow = PATH`, `allow-ro = PATH`, `allow-net = yes|no`, `host-gl = yes|no` (ADR-0041). **Sandbox** (`--sandbox`, ADR-0027, `armor-linux/src/sandbox.rs`, `tech/security.md`): before loading the guest, armor enters user, mount, PID and network namespaces; a supervisor stays outside, an init acts as pid 1, armor continues as pid 2 in a new root with only the allowed paths, under a seccomp filter. **Limits** (`limits.rs`): `--limit-files`, `--limit-processes`, `--limit-file-size`, `--limit-cpu` with `setrlimit` before the path is chosen; `--limit-memory` with `AddressSpace::set_limit` (guest address space counted by armor). The same keys (`limit-*`) in profiles. The command line wins; an unknown key or a wrong value stops armor with the line number. Children relaunched by `execve` receive engine, root, `argv0` and diagnostics as options, and look up their own profile by name (which can add environment and diagnostics). It reads the file and builds argv (`argv[0]` = `--argv0` or the path as it was passed) and envp (armor's environment). It chooses the **guest root** from `--root`, otherwise from `ARMOR_ROOT` (below). The guest's `execve` relaunches armor with these two options and always the engine by name (`--jit`, `--interpreter` or `--lockstep`; ADR-0019, ADR-0028).
2. **Loader** (`armor_linux::loader`):
   - `armor_elf::Elf::parse` validates the header (`ELFCLASS64`, little-endian, `EM_X86_64`, `ET_EXEC` or `ET_DYN`) and the program headers;
   - `ET_EXEC` goes to its own addresses; a PIE (`ET_DYN`) goes to `PIE_BASE` = `0x5555_5555_4000`, as under qemu (`tech/memory.md`);
   - **first** it maps all `PT_LOAD` segments (`AddressSpace::map_fixed`, permissions from `p_flags`), **then** it copies the bytes from the file. This way segments that share a page do not erase each other;
   - the bytes beyond `p_filesz` (bss) stay zero;
   - with `PT_INTERP`: it loads the interpreter (`ld.so`), looked up in the guest root, at a place chosen by the host. Execution starts from its entry point; `ld.so` then loads the libraries by itself with `openat` + `mmap` (ADR-0011);
   - `brk` starts from the end of the executable;
   - with `ARMOR_TRACE_MAPS=1` (since 2026-10-14, a debugging aid) armor prints on stderr where it put the program and the interpreter, and the `mmap` syscall prints every guest file mapping (`armor: map <start>-<end> <file> offset .. prot ..`): private file mappings are copies (ADR-0012), so the host's `/proc/<pid>/maps` does not show the files (`tech/memory.md`).
3. **Initial stack** (`loader::build_stack`):
   - 8 MiB mapped at a place chosen by the host (`map_anywhere`);
   - from top to bottom: execfn, envp and argv strings, `"x86_64"`, 16 random bytes; then the table argc / argv / NULL / envp / NULL / auxv;
   - rsp points to argc and is aligned to 16;
   - auxv: `AT_HWCAP` (CPUID 1, EDX = `0x78bfbfd`: ✅ same value qemu passes, read from the raw auxv of a test program on 2026-10-12; qemu instead does not pass `AT_HWCAP2`, which armor passes as 0), `AT_PAGESZ`(4096), `AT_CLKTCK`, `AT_PHDR`/`AT_ENTRY` (of the executable, shifted by the PIE base), `AT_PHENT`, `AT_PHNUM`, `AT_BASE` (address of the interpreter, 0 without one), `AT_FLAGS`, `AT_UID`/`EUID`/`GID`/`EGID`, `AT_SECURE`, `AT_RANDOM`, `AT_HWCAP2`, `AT_EXECFN`, `AT_PLATFORM`, `AT_NULL`;
   - no `AT_SYSINFO_EHDR` (no vDSO). qemu instead provides one (`tech/syscalls.md`).
4. **Initial CPU state** (`Cpu::new`): all registers at 0 except rsp, RFLAGS = `0x202`. This matches what was observed under qemu (test `basic/initial_state`).
5. **Loop** (`run_thread`):
   - `Cpu::run` executes a block of instructions (at most 10,000) with the page tables locked for reading (`AddressSpace::view`); under the GIL only in lockstep or with `ARMOR_GIL` (ADR-0023). Each instruction is taken from the cache of decoded instructions or read and decoded (ADR-0020), then executed; the block stops at a `syscall`;
   - at startup armor gives its own process the name of the guest program (`PR_SET_NAME`), as `exec` would, and resets SIGPIPE to the default (the Rust runtime ignores it; a new process does not);
   - then `armor_linux::syscall::dispatch` handles the syscall and the loop resumes. `dispatch` also receives a `Process` with the per-process state (brk, executable path for `/proc/self/exe` obtained with `fs::canonicalize` of the program, guest root, live threads, engine to pass to `execve`) and a `syscall::Thread` with the thread's state, including signals (`signal::Signals`).
6. **End:**
   - `exit`/`exit_group` → `std::process::exit(status)`;
   - guest memory fault, #GP (`hlt`, misaligned SSE, instruction > 15 bytes) → message on stderr, then armor terminates with SIGSEGV;
   - #UD (instruction invalid in 64-bit mode, `ud2`, LOCK not allowed) → SIGILL;
   - #DE (division by zero or quotient too large) → SIGFPE;
   - #BP (`int3`) → SIGTRAP;
   - instruction, syscall or use of a syscall not yet supported → message and exit code **125** (`conventions.md`).
7. **Guest root** (`armor_linux::root`, ADR-0013): an absolute guest path `/p` becomes `<root>/p` if it exists, otherwise it stays `/p`; relative paths do not change. Since 2026-10-14 `/proc`, `/sys`, `/dev`, `/run` and `/tmp` (`HOST_ONLY`, whole path components) always come from the host, even if the root has such a directory: unpacked packages bring an empty `/proc`, and Chromium's sandbox then missed `/proc/self/task`. It is the resolution of `qemu-x86_64 -L`, measured with `strace`. It is used by the loader (for `PT_INTERP`) and by the syscalls with paths (`tech/syscalls.md`). The root is `ARMOR_ROOT`; if the variable is not set it is `/usr/x86_64-linux-gnu` when that exists (the x86-64 libraries of `libc6-amd64-cross`); empty means no root.
8. **JIT** (M6, ADR-0021 and `tech/jit.md`; since 2026-10-12 with `--jit`, since 2026-10-13 the default engine, ADR-0028): lookup in the block cache → translated code → translation if absent; untranslated instructions are executed by the interpreter. The host extensions it uses in concurrent mode (FEAT_LSE, FEAT_LRCPC) are read from `AT_HWCAP` when the engine is created; without them the JIT uses the ARMv8.0 substitutes (since 2026-10-14, ADR-0032; `tech/jit.md`, "Every ARMv8.0").
9. **Signals** (M3, ADR-0017, `tech/signals.md`): the host handler records the signal and leaves it blocked; the main loop runs in blocks of 10,000 instructions (`Cpu::run`) and, after each block and each syscall, delivers the pending signals by building an x86_64 frame on the guest stack. Interpreter faults become synchronous signals if the guest has a handler; otherwise armor terminates with that signal.

## Components
The crates live in `crates/<name>/`; `xtask/` lives in the root. Dependencies between crates:
```
armor (bin) ──► armor-linux ──► armor-cpu ──► armor-x86
      │               │              └──────► armor-mem ──► libc
      │               ├──► armor-elf, armor-mem, armor-x86
      │               └──► libc
      ├──► armor-jit ──► armor-cpu, armor-mem, armor-x86, libc
      └──► armor-cpu, armor-elf, armor-mem, armor-x86
```

| Crate | Contents | `unsafe` |
|---|---|---|
| `armor` (bin) | CLI, per-thread main loop (`run_thread`), GIL (`gil.rs`, only outside concurrent mode, ADR-0023), thread start and end, mapping of errors to exit codes and signals; `inspect.rs` (`armor inspect`: ELF/PE/script format, architecture, linking, libraries, extensions used by the code with the length-only decoder, verdict with `loader::check`); `apps.rs` (`armor install`/`run`/`list`/`remove`, ADR-0033); `debs.rs` (`crates/armor/src/debs.rs`: control files and `Packages` indexes, dependency resolution, verified archive indexes (`Packages`, `Contents`) and package downloads for `.deb`, AppImage and archive installs); `engines.rs` (`armor engine fetch`) | forbidden (`forbid`) |
| `armor-elf` | `Elf::parse` (x86-64 executable, for the loader), `Elf::parse_any` and `ident` (any ELF, for `inspect`), interpreter, `DT_NEEDED`, `phdr_address` | forbidden (`forbid`) |
| `armor-x86` | `decode(&[u8]) -> Instruction` and `length(&[u8]) -> Length` (length and extension of any instruction). Modules: `decoder.rs` (prefixes, ModRM/SIB, 1-byte and `0F` maps), `sse.rs` (SSE–SSE3), `maps.rs` (`0F38`/`0F3A`: SSSE3, SSE4.1, SSE4.2), `x87.rs` (x87), `length.rs` (length-only decoder) | forbidden (`forbid`) |
| `armor-cpu` | `Cpu` (registers, rip, rflags, fs/gs base, xmm, mxcsr) and interpreter. Modules: `lib.rs` (loop and integer instructions), `alu.rs` (results and flags), `string.rs`, `sse.rs`, `float.rs` (scalar SSE floating point), `x87.rs` and `f80.rs` (x87 and 80-bit arithmetic), `cpuid.rs`, `icache.rs` (cache of decoded instructions, ADR-0020) | forbidden (`forbid`) |
| `armor-mem` | `AddressSpace` (private and shared mappings, `unmap`, `protect`, 4K permission table) and the `GuestMemory` trait (with `atomic_update` for `LOCK` instructions) | confined here |

**`GuestMemory` trait** (`armor-mem`): `read`, `write`, `fetch`, `code_generation` (ADR-0020), `atomic_update` and `compare_exchange_16` (`LOCK` instructions). The interpreter is generic over this trait, so the unit tests of `armor-cpu` use a fake memory in a `Vec` without mmap.

**Shared decoder:** `armor-x86` serves both the interpreter and the JIT. No intermediate IR: the JIT translates directly from `armor_x86::Op` (ADR-0021; `tech/jit.md`).

## Interpreter (`armor-cpu`)
- **String instructions with `rep`:** as on hardware, every completed iteration stays (rcx, rsi, rdi updated), even if a later iteration faults. Forward `rep stos` and `rep movs` are copied in 4 KiB blocks when the result cannot change: no DF, no overlap, no fault in the block.
- **Atomicity:** an instruction either completes or changes nothing. First result and flags are computed, then memory is written (which can fault), and only afterwards are flags, registers and rip updated. This is verified by the test `faulting_instruction_changes_nothing`.
- **Flags computed immediately** (eager) with 128-bit arithmetic, then truncated to the operand size. Lazy flags exist only in the JIT (`tech/jit.md`); in the interpreter they have not been needed.
- **Fetch:** up to 15 bytes, stopping at the first non-executable page. If the instruction does not fit in the executable bytes, it is an execution fault at the address of the first missing byte.
- **SYSCALL:** sets `rcx` = next rip and `r11` = RFLAGS before handing over to the Linux layer (SDM ✅, see `testing.md` for the discrepancy with qemu).
- **32-bit mode** (ADR-0029, since 2026-10-14): with `Cpu::mode` = `Compat32` the fetch decodes in compatibility mode; 4-byte stack (`push`, `pop`, `call`, `ret`, `enter`, `leave`, `pushf`, `popf`), `rip` and `esp` wrapping at 4 GiB, linear address truncated to 32 bits after the segment base, string instructions, `loop` and `xlat` with `esi`/`edi`/`ecx`/`ebx`. `int 0x80` returns `Step::Syscall` like `syscall`: the Linux layer chooses the i386 table from the mode. Since 2026-10-14 the JIT also translates 32-bit code (`tech/jit.md`, "32-bit code").

## Guest state (`Cpu`)
- Implemented: `regs[16]` (rax…r15), `rip`, `rflags`, `fs_base`/`gs_base` (set by `arch_prctl`; for an i386 guest by `mov fs`/`mov gs` with a TLS selector), `mode` (64-bit or compatibility, ADR-0029), `segments` (selectors of `fs`/`gs` and the TLS entries 12–14 of the GDT from `set_thread_area`), `xmm[16]` (u128), `mxcsr` (initial value 0x1f80; read and written by `ldmxcsr`/`stmxcsr`/`fxsave`/`fxrstor`, default control only, ADR-0015), `x87` (80-bit stack, control and status word; ADR-0016, `tech/floating-point.md`).
- *(planned)* upper half of the `ymm` registers with AVX.

## Thread model (M3, ADR-0018; execution: ADR-0023)
- **1:1:** each guest thread is a host thread (`std::thread`, name `armor-guest`) with its own `Cpu` and its own `syscall::Thread` (signal mask, alternate stack, `clear_child_tid`). The guest's tid is the host's.
- **Shared** (`Guest` in `main.rs`, allocated once for armor's whole lifetime): `AddressSpace` (page tables behind an `RwLock`), `syscall::Process` (path, root, `brk` behind a `Mutex`, number of live threads) and the GIL. Signal actions are an `Arc` shared by all the threads' `Signals`.
- **GIL** (`crates/armor/src/gil.rs`): a ticket lock, only one thread at a time executes guest code. Since 2026-10-13 (ADR-0023) it is used only in `--lockstep` and with `ARMOR_GIL=1`. Before concurrent mode there is only one guest thread, and until 2026-10-13 (evening) it was taken anyway: releasing it woke the `Condvar` with a `futex` syscall at every guest syscall (`tech/performance.md`). In concurrent mode threads run in parallel, with accesses ordered as TSO and atomic `LOCK` (LSE in the JIT, host compare-and-swap in the interpreter; `tech/memory.md`). Syscalls always run in parallel. A turn with the GIL lasts between 5,000 and 10,000 guest instructions (or up to a syscall), a different length each time (`Turns` in `main.rs`, since 2026-10-14): with a fixed length, a thread in a loop that started each turn right after a syscall also ended it at the same point of the loop, and in `c/fork_threads` that point was inside a mutex, so the other threads always found it taken (30–60 s in lockstep instead of 0.25 s). The page tables (`AddressSpace::view`) let a thread waiting to change them go first: without that, a guest thread taking the read lock for every block kept `mprotect` waiting for seconds with the interpreter (2026-10-14).
- **`clone`** (only the POSIX thread flags): `dispatch` returns `Outcome::NewThread`; `start_thread` creates the host thread, takes the tid, writes `CLONE_PARENT_SETTID` and only afterwards lets the child start. The child starts with the parent's registers, rax = 0, the new stack and the new `fs_base`.
- **`exit`** of a thread: clears the `CLONE_CHILD_CLEARTID` word, wakes its waiters (non-private futex, like Linux, for `pthread_join`) and terminates the host thread. The last thread terminates the process. The host's main thread never returns from `main` while other threads are alive. `exit_group` terminates the process.

## Processes (ADR-0019)
- `fork`, `vfork` and `clone` without `CLONE_THREAD`: host `fork()` of the whole of armor. With several threads in the guest (since 2026-10-14) the calling thread first takes the armor locks that the others may hold (page tables in exclusive mode, `brk`, signal actions, and the GIL with `ForkHooks` when there is one), and the child has only that thread, as in Linux (`tech/syscalls.md`). The child has a copy of the address space at the same addresses. `vfork` (also `posix_spawn`) is a fork with copy, in which the parent waits for the child to run `execve` or terminate (an `O_CLOEXEC` pipe).
- `execve` (`crates/armor-linux/src/process.rs`): an x86-64 or i386 ELF (or a `#!` script with such an interpreter) → host `execve` of armor with `--root`, `--argv0` and the same engine, always by name (`--jit`, `--interpreter`, `--lockstep`); everything else → host `execve` as it is. `/proc/self/exe` is the guest program.
- On a host with binfmt_misc for x86-64 (here: qemu), a **native** program that launches an x86 binary starts it under that interpreter, not under armor.

## Address space
**Identity mapping** (guest address = host address), implemented in `armor-mem`. It is feasible because the host has 47-bit VA like the canonical lower half of x86_64. For an i386 guest all mappings are below 4 GiB (`AddressSpace::set_ceiling`, ADR-0029).
- Host pages are always readable and writable.
- Guest permissions are kept in a table with one entry per 4K page and are checked on every access (ADR-0009).
- Host pointers do not leave `armor-mem`, with one exception: `MemView::page_table`, the flat permission table that the code generated by the JIT reads (ADR-0021). The JIT accesses guest memory with its addresses, which are also host addresses.

Details in `tech/memory.md`.

## Calls into the host's libraries (ADR-0041, since 2026-10-15)
Guest stubs make syscall 0x410000 with a function id and sixteen argument slots; `armor_linux::host` calls the matching host function (`dlopen`/`dlsym` from libc) on the guest thread's own host thread and writes the result back; unknown ids give `ENOSYS`, and the stub falls back to the guest's own code (`tech/syscalls.md`).

OpenGL (`--host-gl`, or `host-gl = yes` in a profile or an application's `app.conf`):
- **armor's x86-64 `libGL.so.1`** (`guest/libgl/`, built by `cargo xtask build-guest` into `target/guest/libgl/`, installed by the package in `/usr/lib/armor/x86_64-linux-gnu/`): one stub per OpenGL function (`gl_stubs.c`, generated) and the GLX functions (`glx.c`, by hand). With `--host-gl`, `GuestRoot` gives this file to the guest whenever it opens a `libGL.so.1` or `libOpenGL.so.0` of its root, and the guest's own library under the name `libGL.so.1.armor-guest` (the stubs' fallback when armor does not provide the host's OpenGL).
- **The table** (`crates/armor-linux/src/host/gl_table.rs`, generated): for each of the 2965 functions, its id (FNV-1a of the name), its name and one of 98 C signatures; armor finds the host function with `dlsym` in the host's `libGL.so.1`, or with `glXGetProcAddressARB`. Both files come from Khronos' `gl.xml` (`third_party/khronos/`) through `cargo xtask gl-gen`; `gl-gen --check` fails when they are stale.
- **GLX** (`crates/armor-linux/src/host/glx.rs`): armor opens its own connection to the X server and makes the GLX calls there with the X ids the guest's own `libX11` created (windows, visuals, colormaps are the server's). A visual crosses as its id (the stub rebuilds the guest's `XVisualInfo` with the guest's `XGetVisualInfo`); configs and contexts are opaque values the guest gives back unchanged.
- **What crosses back:** strings the host returns (`glGetString`, `glXQueryExtensionsString`) are copied once into guest memory; `glXGetProcAddressARB` returns the guest's own stub, never a host address. Guest pointers given to the host (vertex arrays, textures, `glReadPixels`) are host pointers (identity mapping above).
- **Not yet:** functions that return memory of the driver (`glMapBuffer`, `glMapBufferRange` and the like) and those that take callbacks (`glDebugMessageCallback`): 20 functions, listed by `gl-gen`; Vulkan and EGL.
